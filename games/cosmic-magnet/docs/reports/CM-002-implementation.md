# CM-002 — сдача

Движок / ОС: Godot 4.5.1 Standard (SHA512 сверен; Windows 10 x64 локально, ubuntu-latest в CI).

## Что изменено

- `data/balance.json` — единственный машиночитаемый источник баланса: параметры магнита/вылета/поля, три типа предметов (гайка 1/1/1, пластина 1/2/3, батарея 2/4/8), три улучшения с `base_cost`/`cost_multiplier`/`max_levels`/`effect` (CM-R06; SPEC: сила 20, радиус +20 за 15, ёмкость +10 за 15, множители 1.6/1.5/1.5, три уровня).
- `scripts/config.gd` — типизированный доступ к конфигу (`CMConfig.i/f/items/upgrades`); числовые константы правил заменены на чтение из JSON; правила расчёта цен сюда не входят.
- `scripts/economy.gd` — только правила экономики: `upgrade_cost = ceil(base × mult^levels)`, атомарная `buy` (лом+уровень одной операцией или ничего), потолки уровней, `effect_sum` по ключам. Лом не может стать отрицательным (покупка отказывается раньше).
- `scripts/game.gd` — машина состояний DOCK↔SALVAGE (CM-R04/R05):
  - заряд тратится только в SALVAGE (`advance_flight`), пустой заряд → авто-возврат;
  - `request_return` — единственная точка возврата (ручная кнопка и обе авто-причины); повторный вызов в DOCK — no-op;
  - `unload` — единственная идемпотентная разгрузка: одно начисление стоимости груза, очистка трюма, восстановление заряда; повторные сигналы ничего не начисляют;
  - полный трюм → авто-возврат без потери добычи (последний предмет учитывается в грузе, затем разгрузка);
  - `register_collection` дополнен правилом «не влезает — не собирается»: предмет остаётся на поле (SPEC «груз не превышает ёмкость»);
  - магазин работает только в DOCK (CM-R07).
- `scripts/magnet.gd` — радиус притяжения из конфига + купленные уровни, перерисовка; магнит движется только в SALVAGE, в DOCK скрыт и заморожен.
- `scripts/salvage_item.gd` — масса/цена из конфига; новая подсказка `FULL` для невлезающего предмета рядом с магнитом; тяжёлый — по-прежнему `S2?` и не собирается.
- `scripts/spawner.gd` — три типа с весами 50/30/20; возрождение предлагает только типы, доступные текущей силе (батареи из стартового микса остаются видимым стимулом; после покупки силы начинают пополняться) — прогресс нельзя заморить покупкой одного направления (SPEC).
- `scenes/main.tscn` — HUD: Scrap/Charge/Cargo/Str-Rad-Cap; правая панель: три кнопки улучшений с ценами/уровнями, RETURN & UNLOAD (в вылете) и янтарная LAUNCH (в доке), статус-строка. Найден и исправлен баг раскладки: офсеты детей панели были абсолютными — кнопки рендерились за экраном (x≈1976); зонд показал rect, исправлено на относительные, добавлена регрессия «все кнопки внутри окна».
- `tools/mouse_timeline.py` — таймлайн ввода для видео: свипы полем + периодические клики LAUNCH/улучшение (кликни-и-смотри: кнопки скрыты/отключены вне своего состояния — промах-клики безопасны).
- `.github/workflows/cosmic-magnet.yml` — шаг «Tests (economy)»; job видео пишет 210 с (6300 кадров) с кликами.

## Фактический тайминг (исправление F1)

Ошибка первой сдачи: «сила 2 куплена в первые ~80 с записи». Факт по CI-артефакту (id 11618626002, просмотрен Codex): первая разгрузка ≈ t=20 с от начала записи, покупка силы 2 ≈ t=22–23 с от начала записи ≈ **18 с от первого вылета** (клик LAUNCH ≈ t=2–4 с). Сила 3 ≈ t=50 с, сила 4 ≈ t=105 с.

Ориентир согласован Эльдаром 2026-10-09 (GAME-SPEC/DEVELOPMENT-PLAN обновлены): 15–30 с от первого вылета при уверенном управлении. CI-маршрут (~18 с) соответствует.

## Закрытие F1 (тесты)

- Арифметический тест переименован в «affordability»: полный трюм гаек ≥ цена первой силы; заряда хватает на уверенный вылет ≥ 15 с. Заявление об измерении времени убрано.
- Добавлен `BENCHMARK`-сценарий (`_test_first_purchase_benchmark`): отдельный экземпляр игры, скриптованный «уверенный» скан поля тем же паттерном, что водит мышью CI-видео; предметы притягиваются/собираются и разгружаются только реальными обработчиками — без прямого заполнения трюма/денег. Печатает фактические отметки: время первой покупки от первого вылета, моменты разгрузок, число вылетов, остаток лома.
- Локальные прогоны (спавн случаен): покупка через **11,8–19,2 с** от вылета (один вылет, значение трюма 37–38). CI-видео-маршрут с тем же паттерном: ~18 с. Benchmark управляемого маршрута, не оценка новичка; живая проба — CM-004.

## Закрытие F2 (регрессия одновременных причин)

`_test_simultaneous_return_reasons_single_payout` переписан: каждый порядок стартует с `cargo = capacity − mass` последнего предмета и почти пустым зарядом — все причины готовы одновременно:
- **A** (полный трюм первым): последний сбор вызывает авто-возврат при charge=0; затем пустой заряд, ручной возврат и два повторных `unload` — no-op. Одна выплата, сброс груза/заряда, сбор в DOCK невозможен.
- **B** (заряд первым): `advance_flight` опустошает заряд при почти полном трюме → авто-возврат; сбор и ручной возврат в DOCK — no-op; повторный `unload` ничего не начисляет.
- **C** (ручная кнопка первой): `request_return` при полном трюме и charge=0; затем заряд и сбор — no-op; одна выплата.
