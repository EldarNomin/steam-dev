# CM-003 — повторная сдача после CHANGES_REQUESTED (2026-10-10)

Ревью: PR #5, head `d75af84` — F1 (P1) бакап, F2 (P1) судьба реликвии, F3 (P2) строгая валидация, F4 (P2) автоперезапись повреждённого. Баланс и темп не менялись (кроме механики выплаты реликвии — суть F2).

## F1 — бакап и сбои записи

- `.bak` обновляется только содержимым **валидного** main (проверка парсингом перед копией): повреждённый main больше не может затереть хороший бакап.
- `copy_absolute` оказался ненадёжным на Windows для файлов, созданных rename (тихо не создавал .bak — поймано зондом): бакап и восстановление main переписаны на явные чтение/запись строки с проверкой результата; `rename` проверяется, при сбое tmp прибирается и `save_data` возвращает false.
- Тесты: битый main + валидный bak → запись успешна, bak держит старые данные, main — свежие; отказ записи при занятом каталогом tmp (false, main цел) и при занятом main (false, bak цел).

## F2 — реликвия больше не теряется

- Реликвия выведена из грузовой модели: её цена (25) начисляется в лом **мгновенно при сборе**, факт находки сохраняется немедленно. Закрытие посреди вылета физически не может её потерять: в грузе её нет. Гейт ёмкости к ней не применяется (полный трюм не мешает находке).
- Регрессия: сбор реликвии → scrap 25 сразу, cargo 0; добавлен обычный груз + `save_on_exit` → в файле scrap 25 и флаг находки, груз сброшен; после перезагрузки scrap 25, реликвия на поле не возвращается.

## F3 — строгая валидация

- `is_valid_save`: scrap/tutorial_stage/уровни — только целые числа без дробной части (JSON-float с нулевой дробью проходит); диапазоны: scrap 0..999 999 999, tutorial 0..99, уровни 0..max_levels из конфига; ключи уровней — ровно три известных, лишние и недостающие запрещены; master_volume — число 0..1.
- Тесты: 11 отвергаемых вариантов (дробный/отрицательный/гигантский scrap, уровень за лимитом, отрицательный/дробный уровень, неизвестный и недостающий ключ уровня, дробный/отрицательный tutorial, строковый scrap) + валидный целочисленный float проходит.

## F4 — повреждённый сейв не перезаписывается молча

- При повреждении и main, и `.bak` их содержимое копируется в диагностические `save_v1.json.corrupt` / `save_v1.json.bak.corrupt` (сами файлы не трогаются).
- `continue_game()` при нечитаемом сейве больше не запускает новый забег молча: показывает подтверждение новой игры; перезапись происходит только после явного подтверждения, диагностические копии переживают её.
- Тесты: битые оба файла → диалог подтверждения + флаг карантина; .corrupt копии с точным повреждённым содержимым; main/bak не изменены до подтверждения; после подтверждения — свежий забег, .corrypt копии на месте.

# CM-003 — правка F5 (2026-10-10)

**F5 (P1):** обновление `.bak` прямой записью `FileAccess.WRITE` неатомарно — crash посреди записи оставлял бы усечённый бакап, уничтожив последнюю валидную копию.

- Введена `_atomic_write(path, content)`: запись во временный файл (`*.tmp`), flush, rename поверх цели, проверка каждого шага; при сбое rename временный файл прибирается, возвращается false.
- Обновление `.bak` и основная запись `save_data` обе идут через `_atomic_write`; восстановление main из бакапа — тоже (тот же паттерн был неатомарным). При сбое обновления бакапа сохранение продолжается с предупреждением — старый `.bak` остаётся последней валидной копией.
- Регрессия (7 проверок): занятый каталогом `*.bak.tmp` → запись сохранения успешна, main свежий, предыдущий `.bak` цел, временный путь без частичного файла; после уборки следующая запись обновляет бакап. Уточнён старый тест сбоев: при отказе основной записи `.bak` держит последнее валидное состояние (56), что и требуется.

Проверки: 37 + 61 + **60** PASS (test_save вырос с 54), import/smoke чисто; CI — в PR.
