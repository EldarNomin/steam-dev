# Передача проекта локальному агенту GLM / z.code

Дата: 2026-10-07. Репозиторий: EldarNomin/steam-dev. Этот документ задаёт рабочий процесс; он не подтверждает доступ GLM к Unity. Первое действие агента — проверить реальный доступ.

## Роли

Эльдар выбирает направление и играет в готовые версии. Локальный GLM работает с проектом и Unity: сцены, компоненты, Console, Play Mode, сборка. Codex работает через GitHub: задачи, спецификации, архитектура, код в согласованных файлах, проверка diff и результатов. Каждый агент пишет в отдельной ветке; на одну задачу назначаем одного исполнителя. Для первой задачи исполнитель — локальный GLM. Codex пока меняет только документы передачи.

GitHub — место обмена результатами, а не автоматический доступ Codex к компьютеру. После локальных изменений GLM делает commit/push. Эльдар сообщает номер PR или commit; Codex проверяет конкретную ревизию. Файлы, которые остались только на компьютере, из этой беседы не видны.

## Первая задача: подтвердить DEV-001 в настоящем Editor

Прочитать [контекст](UnityProjectContext.md) и [DEV-001](../Development/DEV-001.md). Каркас находится в ветке `feature/DEV-001-unity-baseline`, PR №1. В main на момент передачи — документы и правила Git, Unity-каркас туда ещё не слит. Если уже работаешь в ветке PR №1, получи новые документы обычным pull только после проверки рабочего дерева; не переключай ветки и не сбрасывай чужие/несохранённые изменения.

Выполнить последовательно:

1. Найти настоящий корень проекта по Assets, Packages/manifest.json, ProjectSettings/ProjectVersion.txt. Зафиксировать `git status`, текущую ветку/commit, фактическую версию Editor, путь активного проекта. Не создавать поверх папки новый Unity-проект.
2. Проверить инструменты управления Unity безопасным чтением Console и активной сцены/иерархии. Если такого доступа нет, написать точный блокер; не выдавать проверку файлов за подключённый Editor. Использовать уже настроенный пользователем мост, не устанавливать ещё один.
3. Дождаться импорта и компиляции. Прочитать реальные ошибки. Исправлять найденные причины небольшими изменениями; не переписывать весь проект и не обновлять Editor/рендеринг без обоснования. Ожидаемый Editor в каркасе — 6000.3.25f1; при другой фактической версии сначала явно указать расхождение.
4. Создать baseline командой `Cosmic Catch/Setup/Create baseline`, сохранив существующие сцены. Проверить Boot.unity, URP, материалы, build scenes. Сделать снимок Game View в Play Mode: станция, корабль, оранжевая фигура краба, русский экран. Краб неподвижен; это ожидаемое состояние DEV-001.
5. Выйти из Play Mode, повторить Setup и сравнить GUID сцены/материалов и количество Boot в списке сборки. Убедиться, что первая сцена не заменена. Любые результаты этой проверки записывать только после фактического выполнения.
6. Собрать Windows x64, запустить exe. Проверить картинку, текст, кнопку «Выйти» и отсутствие необработанных исключений в Player.log. Успешная компиляция не равна успешной standalone-проверке. Если модуль/лицензия/Windows недоступны, соответствующая строка остаётся BLOCKED.
7. Сохранить созданные Unity-файлы вместе с .meta: сцена, renderer/pipeline, материалы, нужные ProjectSettings и настоящий packages-lock.json. Не публиковать Library, UserSettings, сборки, ключи, токены и локальные пути с персональными данными. Не удалять локальные рабочие файлы ради чистого статуса Git.
8. Записать результат в `Docs/Development/DEV-001-LOCAL-RESULT.md`, приложить один скриншот Game View в `Docs/Evidence/DEV-001/`. Соблюдать имеющиеся LFS-правила для изображений. Логи хранить в игнорируемом Reports; в документ включить относящиеся к задаче сообщения ошибок и указать локальные пути логов. При необходимости приложить очищенный лог к PR, а не коммитить весь Console/Player.log.
9. Commit/push в ветку PR №1 либо отдельную дочернюю ветку с PR в неё, если в PR №1 уже работает другой исполнитель. Перед push проверить, что удалённая ветка не изменилась. Не делать force push и не сливать main без проверки. Сообщить commit и результат пользователю для ревью Codex.

Setup и Build могут менять сцену/настройки нового проекта — это цель DEV-001. Сохранять реальные существующие изменения пользователя. Казино, сеть, движение, сохранения и дополнительный контент в этой задаче не реализовывать.
