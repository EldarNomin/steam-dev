# Unity: технический план и рабочий процесс

Версия 0.1.0. Требования MVP-016–020. Это технический план; актуальный каркас и ограничения проверок описаны в [DEV-001](Development/DEV-001.md).

## Подтверждённое состояние

При первоначальной подготовке ТЗ Unity-проект в EldarNomin/steam-dev отсутствовал. Теперь DEV-001 добавляет Assets, Packages/manifest.json и ProjectSettings/ProjectVersion.txt, asmdef и редакторский генератор стартовой сцены. В текущей рабочей среде Unity Editor/Unity Hub не найдены в PATH; активного Unity MCP среди доступных инструментов нет. Импорт пакетов, сериализованные сцены/настройки, компиляция и сборка пока не выполнены. Сетевые пакеты и MCP не установлены.

Проверенный по файлам контекст: [UnityProjectContext](AI/UnityProjectContext.md). Он явно отличает manifest от разрешённых пакетов и путь будущей сцены от существующего .unity-файла. После реального импорта дополнить фактическими настройками, lock и evidence.

## Предлагаемая структура после создания проекта

```text
Assets/_Game/
  Runtime/Core/          # ID, состояния сессии, правила команд
  Runtime/Hunting/       # существа, трос, приманки, захват
  Runtime/Cargo/         # контейнеры, места, расчёт сдачи
  Runtime/Economy/       # кошельки, покупки, прогресс
  Runtime/Chance/        # ставки, капсулы, гарантии
  Runtime/Networking/    # авторитет, RPC, снимки
  Runtime/Persistence/   # DTO, миграции, запись
  Runtime/Presentation/  # UI, звук, эффекты
  Editor/                # сборка сцен и настройки
  Tests/EditMode/        # формулы и транзакции
  Tests/PlayMode/        # игровые взаимодействия
  Scenes/                # Boot, Station, RockBelt, GasCrater
  Prefabs/
  Definitions/
  Art/
  Audio/
Docs/
```

Изолировать чистые правила RewardCalculator, WalletLedger, ContractProgress, WagerResolver, CapsuleResolver от MonoBehaviour и сетевых RPC. Сеть вызывает те же правила, что solo. Баланс переносится из Docs/Data/balance.v0.1.json в runtime definitions контролируемым импортом; оба источника не редактируются независимо.

Малые asmdef: Game.Domain, Game.Runtime, Game.Editor, Game.Tests. Не строить сложный универсальный фреймворк. Вид существа задаётся definition+поведение, а не копированием всей экономики под каждый prefab.

## Трос и физика

Первая реализация троса: луч для попадания, ограниченная сила/дистанция, LineRenderer для визуала. Нет сложной верёвки из десятков rigidbody. Существа и контейнеры используют ограниченные физические модели; декоративные колебания отделены от авторитетных коллизий. Прототипу требуется измерить силы, массы и поведение при двух тросах; эти коэффициенты пока Unknown.

До второго биома нужно решить ADR-001: достаточен ли NGO+Transport для отзывчивого троса при 100 мс. Если нет — сначала сравнить альтернативную модель управления/синхронизации, а не менять все системы по отдельности. Переход на FishNet/Mirror не предрешён.

## Визуальная политика

Стилизованное 3D, небольшой набор согласованных материалов, читаемые силуэты, один базовый скелет или простые деформации для вида. Цветовые варианты дешевле новых видов, но массивный вариант дополнительно меняет игровой параметр. Первая завершённая сцена показывает дневной/космический свет, контраст инструмента и цели, предупреждения атак и звук натяжения. Проверять картинку скриншотом реального Game View.

Окружение можно собирать из лицензированных ассетов. Для публичного репозитория предпочтительны собственные/CC0 ресурсы. При покупке пакета проверить право публикации исходных файлов; иначе держать их вне публичного Git и документировать воспроизводимый импорт. Нельзя считать платный пакет разрешённым к публичной раздаче только потому, что он куплен.

## Режим работы Эльдар + Codex

1. Эльдар получает каркас DEV-001, добавляет папку репозитория в Hub, открывает и выполняет Setup по [инструкции](Development/DEV-001.md).
2. Проверяем настоящий manifest, сцены и настройки; фиксируем baseline-компиляцию.
3. Codex готовит одну задачу с ID, ожидаемым поведением, допустимыми изменениями и проверкой.
4. Код и редакторские скрипты можно готовить через Git; сцены/префабы предпочтительно изменять в Editor, а не ручным YAML.
5. Эльдар или подключённый инструмент запускает проверку в Unity. Без Editor результат помечается «код подготовлен, runtime не проверен».
6. После проверки сохраняем prefab/scene, коммит и короткую запись результата. Не заканчивать задачу только по отсутствию синтаксических ошибок.

Bezi — необязательный локальный исполнитель внутри Editor. Не является автоматическим доступом этой беседы к компьютеру. При использовании задавать ему маленькую задачу и запрет менять посторонние системы; не запускать два агента на одной сцене одновременно.

Unity Workbench — инструкции для работы, не Unity-side bridge. После создания проекта сначала проверить существующий MCP. При необходимости выбрать ровно один мост по его актуальным инструкциям. Установка пакетов и изменение доступа — отдельное действие; это ТЗ не устанавливает их и не открывает локальный редактор наружу.

## Git и проверки

main — проверенные результаты; feature/<TASK-ID>-<name> — текущая задача. Первоначальные документы можно положить в main, реализация затем через небольшие PR. Сохранять Assets с .meta, Packages/manifest.json и packages-lock.json, ProjectSettings. Игнорировать Unity Library, Temp, Logs, obj и сборки. Текстовая сериализация, Visible Meta Files; после переименований проверять ссылки. Крупные разрешённые бинарные ресурсы — Git LFS.

После изменения правил экономики — EditMode-тесты; после сцен/троса — PlayMode и ручной gameplay; после сетевого изменения — host+client. В будущей CI batchmode-компиляция/тесты требует настоящего Editor и корректной лицензии. Не обещать CI по одному workflow-файлу.

Открытые решения на старте: точный patch Editor, совместимые пакеты, интернет-сервис и его условия, identity migration, параметры физики, конфигурация контроллера игрока. Они не мешают подготовке спецификаций, но закрываются до сетевого milestone.
